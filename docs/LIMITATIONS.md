# Limitations and external dependencies

1. Partially resolved on 2026-08-09. The contract slice is deployed to Monad testnet (chain `10143`, confirmed from the live RPC) with a full address and transaction map in `docs/MONAD.md`. Policy activation and a deposit that recorded on-chain lineage were both executed and verified from their receipts. All eight contracts are `exact_match` source-verified on Sourcify. The console now reads the deployment: the `chain_status` operation performs a direct JSON-RPC read, asserts the reported chain id matches the expected one, decodes `activePolicy`, and records an observation checkpoint (block 52245150, policy v1, `effectiveAt` 1786276174) into `integration_connections`. The remaining gap is that this is a point-in-time RPC read, not an indexer: there is no synced cursor, no reorg handling, and no backfill of historical events. The asset and eligibility oracle are mocks, and `PolicyActivationScheduler` is new unaudited code introduced to make same-block activation reachable from an externally owned account.
2. Resolved on 2026-08-09. Hosted Supabase project `jsdlpkdhenaniejevqdp` (Central EU, Frankfurt) has all nine migrations applied; `suture-orchestrator` and `cleanverse-webhook` are deployed and ACTIVE; the console is deployed at https://suture-one.vercel.app and renders against hosted Supabase. Two consequences. (a) The Edge Function CORS headers were confirmed necessary by experiment: a probe function returning no CORS headers received none from the hosted platform, so without the explicit `Access-Control-Allow-Origin` every browser call to `suture-orchestrator` would be blocked in production. Local Kong injects the header and masks this. (b) Corrected on 2026-08-09. An earlier revision of this document claimed hosted Edge Functions would fail the Cleanverse IP allowlist because they egress from Supabase infrastructure rather than the developer machine. That was inferred, not tested, and it is false. A probe function deployed to the hosted project called `query_apass` and received HTTP 200 with `0000` and an active A-Pass, so hosted egress is authorised. The provider evidence in item 5 is reproducible from the hosted deployment as well as locally. The hosted database has no seeded organisation, so an end-to-end hosted demo requires signing up there first.
3. Resolved on 2026-08-09. Local Edge Function calls failed with `TypeError: Invalid URL: 'http://supabase_edge_runtime_suture-v0.1:8081/…'`. The cause was `project_id`, which the CLI defaults to the working-directory name: the id becomes the container hostname, and a host whose final label is numeric is parsed as an IPv4 address by the WHATWG URL parser, so `…-v0.1` failed to parse before any function was reached. `project_id` is now `suture-v0-1`. A `POST` to `suture-orchestrator` with a valid anon JWT returns the function's own `{"error":"authentication required"}` and its own CORS headers, confirming the function executes. The function's `OPTIONS` handler is still unproven locally because Kong answers preflight itself; that path matters only for a hosted deployment. An authenticated end-to-end preflight decision record remains unproven and depends on item 5.
4. Cleanverse documentation exposes no generic asset-verification endpoint and no credential revocation or policy-change webhook. SUTURE blocks unsupported or unavailable risk evaluation instead of inferring success.
5. Closed on 2026-08-09, with one provenance caveat. A live sandbox preflight produced a `PASS` decision on `VERIFIED` evidence (`atoken` scope, chain `base`, provider request ID `2489d478-7553-4696-a3d5-74666858c6ab`, SHA-256 response digest recorded). All three Cleanverse checks passed: A-Pass active, A-Pass not expired, and A-Token transfer eligibility `apass verify success`. An earlier run against a validator-pool scope produced a `BLOCK` on `VERIFIED` evidence, so both decision directions are demonstrated.
   - **A-Token scope (was caveat a): closed.** The earlier `ComplianceFailed` dead end was a property of the sandbox A-Token available at the time, not of the integration. An A-Token was launched on this account (`0x215d8d76a16A0197CB576d984f68719BE7e69025`, chain `base`, issued `2026-08-09`) and `verify_apass` against it returns `0000` with `data.code 4`.
   - **API-key authorization (was caveat b): closed.** `POST /atoken/launch` requires an AES/CBC envelope keyed on the Base64-decoded api-key. It returned `0000`, which is only possible if Cleanverse decrypted the payload, proving the key is authorized. Read endpoints transmit only `api-id` and could never establish this.
   - **Webhook delivery (was caveat c): closed.** Cleanverse POSTed a genuine signed `ATOKEN_APPLY_RESULT` to the deployed receiver. Delivery `24a2b587-c946-4122-8ec6-07d3a221dc5c` and a second delivery were verified by HMAC, validated, and stored. The first launch returned `ISSUE_FAILED` with `replacement transaction underpriced` — a provider-side chain submission fault; a retry issued successfully. Both outcomes were delivered by webhook, so the failure path is evidenced as well as the success path.
   - **Remaining caveat (d): unrotated key.** The sandbox API key was exposed in cleartext in an assistant session log on 2026-08-09 and could not be rotated. Every result above is reproducible but is not independently trustworthy provenance. Rotate and re-run before citing any of it as evidence.
   - The source asset evidence label was set manually to `verified` to reach the provider path; it is not provider-attested. Cleanverse documents no generic asset-verification endpoint (item 4), so this label can never be provider-derived.

6. Live executor built and proven on 2026-08-09. `suture-executor` submits the authority step to Monad testnet, records the transaction hash BEFORE broadcast, waits for a receipt, and issues an audit receipt bound to the chain result. Verified end to end: tx `0xb0a63d82aeed992f840d4c1f82c968fabdb2d55a8a0342227b85624e11534a83`, block 52238895, plan and incident `resolved`, receipt `execution_mode: external` / `evidence_state: verified`. On-chain `remediation()` returns the correct source, replacement, and asset with status PendingApproval.
   - **Reconciliation is demonstrated, not just implemented.** The first confirmation attempt failed because the initial RPC tried to UPDATE the append-only `remediation_actions` table. The transaction was already mined, so the system was left with on-chain state and an unsettled record — exactly the case reconciliation exists for. After correcting the RPCs to write superseding rows, the reconcile path settled it from chain state alone.
   - Outcomes are append-only: a `confirm:`/`uncertain:` row supersedes the `execute:onchain:` submission, which is never rewritten, so the trail preserves what was believed at submission and what was later observed.
   - The executor performs only the authority step (`openRemediation`). Funding must originate from the source wallet by contract design, so the server never custodies user assets and the release path is not executed here.
   - `MONAD_EXECUTOR_KEY` is currently the deploy key, which is also issuer, policy authority, and approver. Acceptable on testnet, wrong for production: it needs a scoped role with spend limits and rotation.
   - Executor RPCs are service-role only; execute is revoked from `anon` and `authenticated`.
7. Partially resolved on 2026-08-09. The contracts are deployed to Monad testnet and all eight are `exact_match` source-verified on Sourcify for chain 10143. Assurance was raised with 5 invariants (256 runs, 128,000 calls each, 0 failures) covering escrow solvency, funding bounds, executed-implies-fully-funded, policy version monotonicity, and the same-block activation rule; plus 19 unit tests and `forge lint` triage. See `docs/SECURITY_REVIEW.md`.
   - **Still not audited, and this is the item that matters.** The review was written by the same session that wrote the code, so it raises confidence without providing the independence that makes an audit worth anything. `slither` and `mythril` were unavailable, so no symbolic execution or dataflow analysis was performed — the bug classes those tools find best have not been systematically searched for.
   - **Resolved since the review:** the HIGH finding is fixed. A dedicated executor key (`0x96F0B49a557Cd3dE2f2Da419e2b48152a6cC5379`) now holds `policyAuthority` on a redeployed escrow (`0x9E680FD3e2743Ff0691D27FbEA7A3Bf418fa4765`) while the human deploy key retains `approver`. Proven on chain: the full cycle ran with the executor opening and releasing, and approval requiring the separate key. The escrow `release` path is no longer unexercised — 100e18 moved to the replacement wallet and the remediation reached status Executed. `slither` was installed and run: 13 findings, none High or Medium (8 reentrancy-events, 2 reentrancy-benign, 2 timestamp, 1 missing-inheritance), all triaged in `docs/SECURITY_REVIEW.md`.
   - Open findings: `PolicyActivationScheduler` is new session-written code holding policy authority (MEDIUM); and the deployment uses a mock asset and mock oracle, untested against hostile ERC-20 behaviour. The contracts remain unaudited by an independent party, which is the item that matters most.
